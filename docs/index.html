What each mode means

Instructions that did not stick

19 reports

A model disregards an explicit task boundary, repeats an error after correction, or loses an agreed requirement in later work.

Membership test: Can the report identify an explicit instruction or correction followed by work that ignored or reversed it?

Unsupported specifics

16 reports

An answer presents a concrete fact, figure, citation, quote or attribution as established when the report shows it was wrong or had no adequate basis.

Membership test: Did it state a substantive, checkable detail as fact that the report shows was invented, wrong or unsupported?

Procedural detours

13 reports

A model substitutes explanation, unnecessary steps or the wrong order of operations for progress on the requested task.

Membership test: Did the chosen workflow visibly delay or displace a concrete step needed for the requested result?

Claims of work not verified

12 reports

A model says it finished, saved, ran or checked work without evidence that the requested result actually exists or works.

Membership test: Did it present a result as complete or verified when the relevant execution or output was unchecked or contradicted?

Hidden or misreported session state

10 reports

The interface or model obscures or misstates what the session can remember, access or do, or presents synthetic context as a live exchange.

Membership test: Did the account of this session’s memory, continuity, capability or a blocking condition differ from what could be established?

Opaque token and context usage

9 reports

Missing or ambiguous meters or records keep the user from checking how context, overhead or token spend is counted.

Membership test: Was there no trustworthy way to see or reconcile a relevant usage quantity or what contributed to it?

Changes without approval

7 reports

A model commits, moves or creates consequential material before approval or beyond the authorized scope.

Membership test: Did it actually change a repository or file without the review or authorization that applied to that change?

Misread primary records

7 reports

A model overlooks, conflates or misrepresents decisive details in primary material already available to it.

Membership test: Can a reader point to available source material whose wording, scope, sequence or identity the response got wrong?

Fabricated uncertainty

6 reports

A model invents counter-explanations or caveats without evidence, or rebuts a stronger claim than the user made.

Membership test: Did unsupported doubt displace an answer to the actual question or discount evidence without a grounded reason?

Skipped or shallow source checks

4 reports

A model skips a needed lookup or uses inadequate queries, snippets or secondary sources when the claim calls for closer checking.

Membership test: Did a missing or shallow external check materially weaken an answer that called for fresh or primary sources?

Billing without clear consent

2 reports

Overage settings, promotional credits or payment actions are unclear to the user at the point they need to understand or control them.

Membership test: Did a billing setting, credit or access/payment event lack the disclosure or control needed for an informed choice?

How to read these counts

Modes were grouped from behaviors described in the reports. The first tag is the main failure; additional tags mark other behaviors the report documents. Each public Markdown file counts once, even when several files cover the same incident or are revisions.

Severity is a judgment about what the report says happened: harm means a wrong answer reached a real decision, such as the choice to publish advice based on it; waste means time lost or work redone; friction means annoyance only. Potential harm is not counted as an observed decision impact.

Prior logs are marked only when the report records both the instruction to consult earlier failure logs and the repeated failure. An unmarked report may simply lack the evidence. Provider counts use the system responsible for the reported failure, when identifiable. Model labels are taken from the reports, not independently verified.

This is one person’s collection of failures, many written by the models themselves. There’s no denominator for how often each provider was used, so these are counts, not failure rates or a benchmark.
